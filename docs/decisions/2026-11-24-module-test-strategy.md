# Rust 模組以單元測試驗證，主要 CLI 流程以獨立檢查器驗收

## 狀態

accepted（測試方式）。2026-11-24 騎士確認以 Rust 測試碼直接測模組介面、挑選少數主要流程做 CLI 端對端測試，並指定需要合成 FIT 時使用 C# 與 Garmin 官方 FIT SDK。同日騎士確認四表整體結構並授權照規劃實作，後續以 Row 記錄個別修訂。

## 背景

同一條心率規則可產生多個門檻案例。直接測策略能觀察觸發原因與逐點來源。合併器產出的 FIT 另需由獨立解碼器讀回，才能驗證實際寫入的內容。

## 決策

A（Config）、B（Query）、C（Data source）、D（Policy）以 `cargo test` 呼叫 CLI 共用的正式 Rust 模組。時間、樣本及模擬服務回應由各列控制。驗證 FIT 解碼或整個 CLI 流程時，所需的新合成 FIT 由 C# 搭配 Garmin 官方 SDK 編碼，預期值事先定義。CLI 端對端測試另啟程序，有成功輸出的案例再用獨立 inspector CLI 讀回。[單元測試設計](../spec/testcases/module-decision-tables.md#執行方式)

## 影響

可在無私人檔案及無平台憑證的環境測試門檻與錯誤。Rust 能否讀取 Garmin SDK 寫出的樣本、其他實作能否讀取 Rust 的輸出，可分別驗證。現有 Python 雙檔回歸持續提供歷史對照。

## 替代方案

逐列啟動 CLI 會重複造檔、配對與讀回，也較難定位策略門檻的錯誤。整條路徑都用 Rust 造檔與解碼，則容易讓讀寫兩端共享同一種誤解。

## 後續工作

Config 與本機目錄已接入 Rust 單元測試。C# 測試檔產生器供新增 FIT 案例使用。接續補上日期查詢、配對與策略案例。CLI 自動化先挑本機輸出、品質阻擋及發佈續查；真實平台驗收沿用 M13。[端對端驗收的代表流程](../spec/testcases/merger.md#端對端驗收的代表流程)
